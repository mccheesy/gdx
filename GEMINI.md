# Gemini Code Assist Project Guide: gdx

This document serves as the primary guide for Gemini Code Assist to ensure it has the necessary context to contribute effectively to the `gdx` project.

## 1. Project Mission

**`gdx`** is a command-line interface (CLI) tool written in Go. Its purpose is to bootstrap and manage project-specific, containerized development environments for the Godot Engine. The primary goal is to simplify the setup process for developers, particularly on container-native operating systems like Fedora Atomic Desktops (Bazzite, Universal Blue, etc.).

The main command, `gdx init`, will create a new project directory, clone a base Godot game template, and then generate a custom `Dockerfile` and `README.md` based on an interactive setup session with the user.

## 2. Core Technologies & Personas

*   **Language**: **Go**. All generated code should be modern, idiomatic, and well-documented Go.
*   **CLI Framework**: **Cobra**. We will use Cobra to structure the CLI commands (`gdx`, `gdx init`, etc.).
*   **Interactive UI**: **Bubble Tea**. The interactive setup for the `init` command will be built using the Bubble Tea framework for a polished terminal user experience.
*   **Containerization**: **Docker/Podman**. The tool generates a `Dockerfile` that builds a Fedora-based image. All package management within the Dockerfile must use `dnf`.
*   **Persona**: You are Gemini Code Assist, a world-class software engineering assistant. Your goal is to provide high-quality, clean, and well-explained code that adheres to the project's specifications.

## 3. Key Feature: `gdx init`

The `init` command is the cornerstone of the project. Its execution flow is as follows:

1.  **Command Execution**: `gdx init "My Project Name"`
2.  **Directory Creation**: Create a directory named `my-project-name`.
3.  **Template Cloning**: Clone the `https://github.com/Chickensoft/GodotGame` repository into this new directory.
4.  **Interactive Setup (Bubble Tea)**: Launch a terminal UI to ask the user the following:
    *   **IDE Selection** (multi-select):
        *   Neovide (Neovim Nightly)
        *   Visual Studio Code
        *   JetBrains Rider
        *   Geany
    *   **Toolset Selection** (single-select):
        *   **2D**: Aseprite, Krita, Tiled Map Editor
        *   **3D**: Blender, Krita, Aseprite
5.  **File Generation**: Based on the user's selections, generate the following files inside the project directory:
    *   `Dockerfile`: A dynamically constructed file.
    *   `README.md`: A personalized readme with build/run instructions.
    *   `desktop-files/`: A directory containing `.desktop` files for all selected applications (including Godot).
    *   `vscode.repo`: (If VS Code is selected) A yum repository file.

## 4. Dockerfile Generation Strategy

The `Dockerfile` will be generated by combining modular blocks of text. The `Dockerfile.sample` in the repository serves as a comprehensive template for all possible options.

*   **Base**: Always start with `FROM fedora:latest`.
*   **Core Dependencies**: Always include `git`, `wget`, `.NET SDK`, and base GUI libraries.
*   **Godot**: Use the [GodotEnv](https://github.com/chickensoft-games/GodotEnv) .NET tool to always install the Mono version of Godot (version 4.5.0 by default).
*   **Conditional Blocks**: Include installation steps for IDEs and toolset applications only if they were selected by the user.
*   **Package Management**: Use `dnf`. For tools not in the main Fedora repos, use COPRs or download them directly via `wget`.
*   **Best Practices**:
    *   Combine `RUN` commands where logical to reduce image layers.
    *   Clean up `dnf` cache (`dnf clean all`) at the end of installation layers.
    *   Use `ARG` and `ENV` for version numbers to make updates easier.

## 5. Development Plan

We will build the `gdx` tool incrementally. The proposed order of implementation is:

1.  **Phase 1: CLI Scaffolding**
    *   Set up the Go module (`go mod init`).
    *   Create the basic Cobra command structure for `gdx` and the `gdx init` subcommand.
    *   Implement the project name argument handling and directory creation.

2.  **Phase 2: Interactive UI**
    *   Design and implement the Bubble Tea model (`model.go`) for the interactive setup.
    *   Integrate the Bubble Tea program into the `init` command's execution flow.

3.  **Phase 3: File Generation Logic**
    *   Implement the logic to clone the Git template.
    *   Create a `templates` package in Go to manage the dynamic generation of the `Dockerfile` and `README.md`.
    *   Use Go's `text/template` package for robust template rendering.

4.  **Phase 4: Future Commands**
    *   Implement `gdx build`, `gdx launch`, and `gdx enter` as specified in the project document.

## 6. Code Style and Conventions

*   Follow standard Go formatting (`gofmt`).
*   Write clear, concise comments explaining non-obvious code.
*   Structure the project logically (e.g., `cmd/` for commands, `internal/` for application logic, `internal/tui` for Bubble Tea components).
*   Handle errors gracefully and provide user-friendly error messages.
